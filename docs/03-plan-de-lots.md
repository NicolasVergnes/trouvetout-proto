# Plan de lots — v1 (P0 + P1 d'un seul tenant)

Le périmètre v1 est livré en une seule version, mais construit par lots ordonnés : chaque lot laisse le dépôt dans un état compilable et testé sur les deux plateformes. Un lot n'est « terminé » que si ses critères passent en CI et que les trois revues (sécurité, Android, iOS) n'ont pas d'objection bloquante.

Statut à tenir à jour dans ce fichier (☐ à faire, ◐ en cours, ☑ terminé).

## Lot 0 — Fondations du dépôt ☑
- Monorepo KMP : `shared` (commonMain/androidMain/iosMain), `androidApp` (Compose, minSdk 29, targetSdk courant), `iosApp` (SwiftUI, iOS 16, framework KMP via SPM/CocoaPods ou embedAndSignAppleFrameworkForXcode).
- Versions épinglées (`libs.versions.toml`), ktlint/detekt, SwiftLint, SwiftFormat, `.editorconfig`.
- CI (GitHub Actions ou équivalent) : `./gradlew :shared:allTests :androidApp:assembleDebug` sur Linux ; `xcodebuild test` sur macOS.
- Scripts `tools/check-deps.sh` (dépendances interdites, permissions) et `tools/check-network.sh` (squelette).
- Critères : les deux apps démarrent sur un écran vide ; CI verte ; hooks Claude Code actifs.

## Lot 1 — Socle de données (A1–A4, A6, A10, N9) ☑
- Entités, journal d'événements, projection `location_state`, SQLDelight, migrations, `meta`.
- Vérification des dépendances Gradle (`gradle/verification-metadata.xml`) : recommandée par la revue sécurité du lot 0, livrée au lot 2 (ADR-017).
- Stockage des photos (compression, miniatures, exclusion des sauvegardes système).
- `docs/format-export.md` : schéma SQL et JSON publiés.
- Tests : `replay(events) == state` sur 50 scénarios ; propriétés (un item a toujours un état) ; performance N7 (10 000 objets / 100 000 événements) en test JVM.
- Critères : couverture des use cases Store/Take/Return/MoveTo/Lend ; aucune requête SQL non paramétrée.

## Lot 2 — Export / import (A7, A8, A13 corbeille, H6 suppression) ☑
- ZIP `manifest + events.jsonl + snapshot.json + photos/`, feuille de partage système ; import en flux avec validations (taille, chemins, zip bomb) ; fusion par `id` d'événement.
- Corbeille 30 jours (purge des photos), annulation de la dernière action (événement inverse).
- Suppression totale : fichiers (base + `-wal`/`-shm`, `photos/`, `exports/`, `imports/`) ; l'instance `SharedFactory` est épuisée après `wipeAllData()` et l'hôte en recrée une. Clés (lot 8), préférences et notifications (lot 9) s'ajouteront à la procédure quand ils existeront.
- Vérification des sommes des dépendances Gradle (`gradle/verification-metadata.xml`) : fichier généré par le workflow `Dependency verification metadata` (Linux puis macOS) et fusionné localement, vérification stricte sur les deux jobs (ADR-017).
- Critères : export → suppression totale → import = état identique (test automatisé sur les deux plateformes) ; un export v1 fabriqué à la main avec des champs inconnus s'importe (N9).
- Suites consignées par les revues du lot : (a) inflater `events.jsonl` ligne à ligne au lieu d'une entrée en mémoire (plafond 64 Mio en attendant) ; (b) ZIP64 ou export multi-volumes avant le lot 7 (les photos pleine taille peuvent dépasser 4 Gio) ; (c) tests Compose de l'écran Réglages (`busy`, confirmation d'effacement, textes de refus) et aller-retour export → effacement → import sur appareil Android (avec les tests de plateforme du lot 4) ; (d) tests manquants : `EVENTS_TOO_LARGE`, `TOO_MANY_EVENTS`, photo > 48 Mio, ligne > 64 Kio ; (e) `viewModel {}` hors NavHost : le NavHost du lot 3 doit porter le ViewModel des réglages (état consommé en événement unique).

## Lot 3 — Capture texte et parseur (B4, B7, B11, B12, B14, A14, I4) ☑
- `shared/capture` : normalisation, intents FR/EN, extraction objet/lieu/quantité/personne, résolution de lieu par similarité (distance d'édition d'abord ; embeddings branchés au lot 6), alias, multi-objets.
- Détection de doublons à la saisie (A14) par similarité de nom.
- UI minimale de capture texte (Compose + SwiftUI) avec autocomplétion des lieux et carte de confirmation (B6) ; désambiguïsation (B7).
- Corpus `corpus/parser.jsonl` (≥ 150 phrases FR, ≥ 60 EN) et test de non-régression : ≥ 95 % d'intents corrects, ≥ 90 % de découpe objet/lieu exacte. État : 159 FR + 77 EN, 100 % / 100 % (`./gradlew :tools:evalParser`).
- Critères : U1 en texte, U5, U6 passent ; seuils du corpus atteints.
- Suites consignées : (a) recherche réelle derrière les questions au lot 6 (aujourd'hui filtre sur le nom) ; (b) écran de capture = écran d'accueil sans NavHost, à poser avec les écrans de lieux du lot 4 ; (c) H3 (`FLAG_SECURE`, vue floutée) et le masquage des objets sensibles dans la liste d'accueil arrivent au lot 8 ; question ouverte sur l'apprentissage du clavier dans `docs/04-decisions.md` ; Android n'explique pas encore un stockage indisponible (iOS le fait) ; (d) le mode « je range » par lot (B10) arrive au lot 5 ; (e) tests Compose / XCUITest du parcours U1 texte avec les tests de plateforme du lot 4.

## Lot 5 — Capture vocale et points d'entrée (B1, B2, B5, B6, B10, C5, N1) ☑
- Transcription sur l'appareil (SFSpeech on-device / SpeechRecognizer offline), détection d'indisponibilité, repli texte ; pack Whisper optionnel seulement si nécessaire après mesure.
- Widgets écran d'accueil et verrouillé, bouton Action (App Intent), tuile Android, activité/scène de capture transparente.
- Mode « je range » par lot (B10). Question vs affirmation (C5) : « où est… » déclenche la recherche.
- Mesure N1 sur appareils de référence (test instrumenté avec audio préenregistré).
- Critères : U1 complet (widget → voix → fiche) ; aucun flux audio ne quitte l'appareil (vérifié par `check-network`).
- État (ADR-020) : voix seulement quand la reconnaissance sur l'appareil est garantie (`SpeechPolicy` ; Android 12+ `createOnDeviceSpeechRecognizer`, iOS `requiresOnDeviceRecognition`) ; Android 10–11 en saisie texte expliquée (la tuile et le widget y ouvrent directement le clavier) ; permission au premier usage après explication ; source `VOICE` ; mode « je range » (`CaptureService.proposeIn`) ; Android : `CaptureActivity` translucide, widget RemoteViews, tuile ; iOS : `CaptureIntent` + App Shortcuts (Siri, Raccourcis, bouton Action), extension WidgetKit écran d'accueil et verrouillé, schéma `trouvetout-proto://capture` (une écoute ouverte par URL n'enregistre rien sans tap). `tools/check-network.sh` vérifie statiquement la reconnaissance sur l'appareil et les widgets sans accès au noyau. Tests : `SpeechPolicyTest`, `CaptureServiceTest` (B10), `QuickCaptureTest` (API 29), `CaptureEntryTests` et `CaptureVoiceTests` (XCTest). Vérifié à la main : tuile et panneau sur API 29 (texte) et API 36 (explication, permission, écoute par le service sur l'appareil ; l'émulateur n'a pas de pack de langue).
- Suites consignées par les revues du lot : (a) **sur appareil** : dictée réelle et U1 complet (widget → voix → fiche) sur un Android 12+ avec pack hors ligne et sur iPhone, mesure N1, ordre des événements au réveil par intent/URL, texte de l'invite système « Reconnaissance vocale » d'iOS 16 (au besoin, préciser l'explication de l'app) ; (b) proposer le pack de langue avant l'écoute (`checkRecognitionSupport` / `triggerModelDownload`, API 33) ; (c) tests Compose du mode « je range », de l'explication puis du refus de permission et de l'arrêt du micro quand on quitte l'accueil ; XCUITest du parcours U1 ; (d) lot 8 : `FLAG_SECURE` aussi sur `CaptureActivity`, objets `sensitive` masqués dans les questions de la capture rapide, `authenticationPolicy` explicite sur `CaptureIntent`, micro du clavier (dictée du clavier hors du contrôle de l'app) avec la question ouverte sur l'apprentissage du clavier ; (e) Android : retour visible quand une capture rapide n'écrit rien (« déjà rangé là »), aperçu du widget sur API 29–30 (`previewImage`) ; (f) iOS : callbacks audio et d'autorisation `@Sendable` avant Swift 6, `shortTitle` / `systemImageName` des App Shortcuts (iOS 17), `captureLang` exposé une seule fois (dette (g) du lot 4), `FRAMEWORK_SEARCH_PATHS` limité aux cibles qui lient le noyau ; (g) J7 : paragraphe « Micro et dictée » (reconnaissance sur le téléphone, son jamais enregistré, **la phrase est conservée dans l'historique et les exports** comme une phrase tapée) et « widgets, tuile et Siri n'affichent aucun objet » ; fiche Data safety : déclarer `RECORD_AUDIO` ; (h) parcours dynamiques de `check-network` au lot 12.

## Lot 6 — Recherche hybride et modèle embarqué (C1–C4, C11, C12, N2, N3) ☑
- FTS5 tolérant, synonymes FR/EN, `TextEmbedder` (interface) + implémentation EmbeddingGemma 2 texte via LiteRT sur les deux plateformes, `ModelSelector` (RAM), pack à la demande avec SHA-256, réindexation sur changement de modèle.
- Fusion RRF + récence/fréquence ; réponse en une ligne (C4) ; filtres (C11) ; suggestions (C12, sans objets sensibles).
- `corpus/recherche.jsonl` (300 questions) et `tools/eval-search` en CI : 80 % top-1, 95 % top-3, < 1 s / 5 000 objets.
- Critères : U3 ; recherche utilisable sans pack (mot-clé) avec message explicite ; mémoire < 350 Mo en texte seul.
- État (ADR-021) : index mot-clé **en mémoire** (pas de FTS5, absent du SQLite d'Android) avec fautes, préfixes et synonymes FR/EN ; EmbeddingGemma 2 Text 270M **inclus dans l'app** (téléchargé au build depuis une révision épinglée, SHA-256 vérifié, jamais versionné ; aucune permission réseau) et exécuté par LiteRT-LM 0.19.0 sur les deux plateformes ; vecteurs float16 en cache (`embedding`, schéma 2, migration additive), calculés au premier plan, modèle libéré en arrière-plan ; fusion linéaire réglée sur le split `dev` du corpus ; réponse en une ligne (C4) avec fil d'Ariane cliquable (C6) et photo, filtres (C11), suggestions sans objet sensible (C12) ; écrans de recherche Compose et SwiftUI, question de l'accueil (C5) vers la recherche ; section « Recherche » des réglages (licences Apache 2.0). Corpus : 406 fiches, 360 questions + 20 absentes (`corpus/build-search-corpus.py`), écrit puis audité par des passes indépendantes du moteur. Mesures (`tools/eval-search`, job CI `search-eval`) : **hybride FR 82,3 % top-1 / 92,3 % top-3, EN 96,7 % / 100 %** (holdout FR 75,0 % / 81,7 %) ; mots-clés seuls FR 63,3 % / 73,7 % ; latence p95 132 ms sur 5 000 objets (N2 tenu) ; U3 vérifié sur l'émulateur API 29 ; mémoire avec le modèle chargé 212 Mo sales (PSS 434 Mo, fichier projeté compris). Tests : `KeywordSearchTest`, `VectorsTest`, `SearchServiceTest`, `ModelSelectorTest`, `PlaceTreeTest`, `MigrationTest`, `SearchCorpusTest` (plancher mot-clé), `TextModelTest` (API 29), `SearchModelTests` (XCTest).
- Suites consignées : (a) **N3 en français : top-1 atteint (82,3 %), top-3 non (92,3 % pour 95 %)** ; la CI bloque sous le plancher `SearchCorpus.FLOORS` (FR 81,5 % / 91,5 %, EN 95 % / 98 %) qui ne baisse jamais ; pistes : lexique de marques et de mots familiers construit depuis une source indépendante, avec un nouveau holdout écrit à l'aveugle (les manques restants sont surtout des synonymes : moka, PQ, turbulette…), variante 440M/740M sur ≥ 6 Go (lot 7), reclassement par le petit LLM (lot 11) ; détection des objets absents (2/20) par un seuil de confiance sur la réponse en une ligne ; (b) **livraison Play** : pack d'assets *fast-follow* au lot 12 (limite de 200 Mo du module de base ; supprime la copie dans `cacheDir`, aujourd'hui ≈ 2 × 165 Mo + 71 Mo de cache XNNPACK sur le téléphone) ; (c) **sur appareil** : latence et mémoire sur un Android 10 à 4 Go et un iPhone 8 (mesures faites sur PC et émulateur), XCTest `SearchModelTests` à valider sur iPhone réel ; (d) tests Compose et XCUITest de l'écran de recherche (filtres, suggestions, réponse, mode « mots-clés seulement ») ; (e) « rien trouvé » pour un objet absent proche d'un objet présent (« fer à friser » → fer à repasser) : la réponse en une ligne pourrait n'apparaître qu'au-dessus d'un seuil de confiance ; (f) embeddings branchés sur `PlaceResolver` et `DuplicateDetector` (prévu au lot 3) non faits : à mesurer sur `corpus/parser.jsonl` sans dégrader la capture ;
