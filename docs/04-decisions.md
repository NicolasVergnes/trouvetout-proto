# Journal des décisions (ADR)

Format : date, décision, raison, conséquences. Ajouter une entrée à chaque choix structurant ; ne jamais modifier une entrée passée, en ajouter une nouvelle qui la remplace.

## ADR-001 — 2026-10-23 — Local d'abord, sans compte ni serveur
**Décision** : toutes les données vivent sur le téléphone ; aucun backend ; aucune télémétrie.
**Raison** : positionnement défendable face aux plateformes (Google Find Hub est cloud), RGPD par construction, coût d'exploitation nul permettant un achat unique.
**Conséquences** : partage multi-appareils plus complexe (reporté, voir ADR-005) ; essai gratuit ancré sur les magasins ou en local (ADR-007).

## ADR-002 — 2026-10-24 — Kotlin Multiplatform + interfaces natives
**Décision** : moteur (base, journal, capture, recherche, modèles, licence) en KMP ; UI Jetpack Compose sur Android, SwiftUI sur iOS.
**Raison** : une seule implémentation de la logique et du format de données ; rendu et intégrations système natifs (widgets, App Intents, parole, achats).
**Conséquences** : build iOS via framework KMP ; `expect/actual` pour fichiers, RAM, crypto, parole ; pas de Flutter/React Native.

## ADR-003 — 2026-10-24 — EmbeddingGemma 2 embarqué, variante selon la RAM
**Décision** : un seul modèle d'embeddings dans l'app ; omnimodal (740 M) si RAM ≥ 6 Go, texte seul (270 M) sinon ; APIs système en bonus, jamais requises.
**Raison** : couvrir ~75 % du parc (dont les téléphones de plus de 4 ans) au lieu des 15–20 % équipés d'IA système ; même espace vectoriel texte/image sans second modèle.
**Conséquences** : packs téléchargés à la demande ; `model_id` sur chaque vecteur ; réindexation depuis le texte source si la variante change ; validation FR à faire sur le corpus.

## ADR-004 — 2026-10-24 — Pas de LLM pour l'extraction en v1
**Décision** : le parseur de phrases est à base de règles + similarité avec les lieux connus ; l'extraction par LLM (B3) est en P3 ; la réponse générative (C13) est un pack optionnel en dernier lot.
**Raison** : déterminisme, latence, couverture des appareils anciens, testabilité par corpus.
**Conséquences** : corpus `parser.jsonl` obligatoire ; formulations exotiques traitées par la désambiguïsation (B7) plutôt que par la génération.

## ADR-005 — 2026-10-24 — Foyer et partage reportés en P3
**Décision** : la v1 est mono-utilisateur, mono-appareil ; la section F entière est reportée.
**Raison** : livrer vite une v1 utile ; le partage sans serveur demande une architecture dédiée.
**Conséquences** : le journal d'événements (deviceId, actor, horodatage) est néanmoins construit dès la v1 pour permettre la fusion plus tard sans migration ; architecture retenue pour la v2 : synchronisation de proximité d'abord, relais chiffré aveugle ensuite.

## ADR-006 — 2026-10-24 — Versions minimales iOS 16 / Android 10
**Décision** : iOS 16 (iPhone 8/X, 2017) et Android 10 (API 29, 2019).
**Raison** : toucher un large public qui garde son téléphone plus de 4 ans ; ~90 % du parc Android, ~95 % des iPhones actifs.
**Conséquences** : repli non-IA (mot-clé + règles) obligatoire partout ; budgets mémoire serrés sur 2–4 Go ; APIs récentes (Foundation Models, Gemini Nano) encapsulées derrière des interfaces optionnelles.

## ADR-007 — 2026-10-24 — Essai gratuit 6 mois puis blocage des seuls ajouts
**Décision** : 6 mois d'usage complet sans compte ; ensuite, les nouvelles fiches sont bloquées, tout le reste reste libre (recherche, modification, export, suppression). Tarif à trancher : 10 € unique ou 2 €/an.
**Raison** : ne jamais prendre les données de l'utilisateur en otage ; modèle compatible avec l'absence de serveur ; ancrage fiable côté Apple (`AppTransaction.originalPurchaseDate`), approximatif côté Android (accepté).
**Conséquences** : StoreKit 2 / Play Billing dès la v1 (J5 remonté en P1) ; écran d'échéance non bloquant ; pas de validation serveur des reçus.

## ADR-008 — 2026-10-24 — Pas de plafond strict de taille d'app
**Décision** : viser léger, mais ne pas sacrifier de fonction pour rester sous 60 Mo ; les modèles restent hors binaire, en packs à la demande.
**Raison** : la contrainte était arbitraire ; les mécanismes de livraison (Play Asset Delivery, On-Demand Resources, téléchargement HTTPS vérifié) existent.

## ADR-009 — 2026-10-24 — Pas d'enquête utilisateurs préalable
**Décision** : le corpus de test (300 questions, 150+ phrases de capture) est construit par le développeur à partir de phrases synthétiques et de son usage.
**Conséquences** : marquer dans le corpus l'origine des phrases pour pouvoir, plus tard, remplacer les synthétiques par des réelles.

## ADR-010 — 2026-10-24 — « TrouveTout » est un nom de prototype
**Décision** : ne pas figer de nom de marque dans les identifiants techniques exposés (bundle id, package name, nom de schéma d'URL, domaine) avant le choix définitif ; utiliser un identifiant neutre interne (ex. `app.trouvetout.proto` ou un nom de code) et une constante unique `AppName`.

## ADR-011 — 2026-10-24 — Identifiants techniques neutres
**Décision** : packages Kotlin `app.trouvetout.core` (shared) et `app.trouvetout.android` (androidApp) ; `applicationId` et bundle id `app.trouvetout.proto` ; schéma d'URL `trouvetout-proto://` ; le nom affiché vient d'un seul objet `AppInfo`.
**Raison** : application de l'ADR-010 — rien de la marque dans les identifiants exposés avant le choix définitif.
**Conséquences** : renommer l'app = changer `AppInfo`, les chaînes et les identifiants des magasins ; le code ne change pas.

## ADR-012 — 2026-10-24 — Chaîne de build et pont iOS
**Décision** : Kotlin 2.4.21, Gradle 9.7.0, AGP 9.3.x ; `shared` utilise le plugin `com.android.kotlin.multiplatform.library` (AGP 9 interdit `com.android.library` + KMP dans un même module) ; `androidApp` utilise le Kotlin intégré d'AGP 9. Injection **manuelle** (`SharedFactory`), pas de Koin. Pont Swift **manuel** (`FlowWatcher` en commonMain + `Shared+Swift.swift`), pas de SKIE. Projet Xcode **généré par XcodeGen** (`iosApp/project.yml` versionné) ; framework statique via `embedAndSignAppleFrameworkForXcode`, pas de CocoaPods.
**Raison** : développement sur Windows sans Xcode — le moins de pièces possible que l'on ne peut pas tester localement ; un `.pbxproj` écrit à la main serait fragile.
**Conséquences** : la compilation et les tests iOS n'ont lieu que sur la CI macOS ; `swift`/`xcodebuild` ne sont jamais lancés en local ; chaque exposition d'un `Flow` à Swift passe par `FlowWatcher`.

## ADR-013 — 2026-10-24 — Dépôt public et flux git sans PR
**Décision** : dépôt GitHub public `trouvetout-proto` (minutes GitHub Actions illimitées, macOS compris) ; une branche `lot/NN-*` par lot, poussée pour la CI, fusionnée localement dans `main` (`--no-ff`) sans pull request ; revues faites par `/code-review` et les agents du projet avant la fusion.
**Raison** : la CI macOS est la seule vérification iOS ; les PR n'apportent rien tant qu'il n'y a qu'un développeur et un agent.
**Conséquences** : le code du prototype est visible ; pas de licence pour l'instant (tous droits réservés) — voir « Questions ouvertes ».

## ADR-014 — 2026-10-24 — Deux produits d'achat
**Décision** : précise l'ADR-007 — l'écran d'échéance propose **les deux** produits : déblocage non consommable à 10 € et abonnement annuel à 2 €/an ; `purchased` est vrai si l'un des deux est actif.
**Raison** : laisser le choix à l'utilisateur ; coût d'implémentation acceptable avec StoreKit 2 / Play Billing.
**Conséquences** : deux identifiants de produit à configurer dans chaque console (lot 10) ; les deux états à tester (y compris abonnement expiré → ajouts bloqués de nouveau).

## ADR-015 — 2026-10-24 — Socle de données (lot 1)
**Décision** : SQLDelight 2.4 (dialecte SQLite 3.25 = plancher d'Android 10) avec un fichier `.sq` par table et des requêtes nommées ; payloads d'événements typés (`EventPayload` scellé) sérialisés en JSON par kotlinx.serialization avec discriminant `type` et lecture tolérante (`ignoreUnknownKeys`) ; identifiants ULID générés en Kotlin commun (générateur monotone par écrivain) ; instants `kotlin.time.Instant` (stable depuis Kotlin 2.3) stockés en millisecondes UTC ; `EventStore.append` = transaction « insérer + indexer les sujets + projeter », rejeu complet si un événement plus ancien que la tête arrive ; projection écrite uniquement par `Projector` avec des `INSERT OR REPLACE` idempotents ; photos ré-encodées par un `ImageCodec` de plateforme (Android `BitmapFactory` + orientation EXIF, iOS `UIImage` via l'adaptateur `NSDataImageCodec`, JVM `ImageIO` pour les outils) et stockées via une abstraction `FileStore` ; source set `jvmCommon` (Android + JVM) pour n'écrire qu'une fois les `actual` java.*.
**Raison** : même schéma et même format sur les deux plateformes, rejouabilité prouvée par tests (50 scénarios aléatoires, convergence de deux journaux), aucune dépendance de plateforme dans `commonMain`.
**Conséquences** : la table FTS5 arrive au lot 6 par migration additive ; `docs/format-export.md` publie le schéma et le format d'événements ; toute nouvelle table ou colonne = migration `.sqm` additive + mise à jour du document.
**Précisions après revue** : (a) un payload inconnu ou indécodable devient `EventPayload.Unknown` (type + JSON brut), conservé dans le journal, ignoré par la projection, réexporté tel quel — le décodage ne lève jamais et ne met jamais de texte métier dans un message d'exception ; (b) l'archivage est un drapeau de la fiche, pas un état de lieu : `location_state.state` vaut `STORED | TAKEN | LENT` (écart assumé avec `01-architecture.md` §3.1, qui listait `archived`) pour qu'archiver ne perde jamais un prêt en cours ; (c) l'ordre canonique du journal est le triplet `(at, deviceId, id)`, y compris pour détecter un événement arrivé en retard ; (d) `SharedConfig.storageReady = false` fait refuser l'ouverture de la base quand l'hôte n'a pas pu garantir le répertoire hors sauvegarde.

## ADR-016 — 2026-10-26 — Export, import, corbeille, annulation, suppression totale (lot 2)
**Décision** : (a) l'archive ZIP est écrite et lue par un lecteur/écrivain **en Kotlin commun** (`data/export/Zip.kt` : entrées stockées ou deflate, CRC-32 vérifié, répertoire central lu d'abord), avec deflate/inflate bruts en `expect/actual` (`java.util.zip` côté JVM/Android, `zlib` côté iOS) ; aucune bibliothèque tierce. (b) Lecture et écriture **en flux** via `FileStore.sink` / `FileStore.source` (`ByteSink`, `RandomAccessSource`) : l'archive n'est jamais chargée entière en mémoire ; une entrée l'est (photo ≤ 48 Mio, `events.jsonl` ≤ 64 Mio — l'inflation ligne à ligne est un suivi noté dans `03-plan-de-lots.md`) ; un échec d'écriture abandonne le fichier temporaire (`ByteSink.abort`), la cible n'apparaît jamais tronquée. (c) L'import est **borné et strict** : 200 000 entrées, manifeste ≤ 1 Mio, `events.jsonl` ≤ 64 Mio et ≤ 1 000 000 lignes de ≤ 64 Kio, photo ≤ 48 Mio, archive copiée par l'hôte ≤ 1 Gio, noms de photos validés dans l'archive **et** dans les événements `PhotoAttached` (`<ULID>.jpg` / `<ULID>_t.jpg`), identifiants ≤ 64 caractères, instants dans [1970, 3000] ; une ligne invalide est comptée et ignorée, un payload inconnu est conservé (`EventPayload.Unknown`), un `formatVersion` supérieur est refusé (`FORMAT_TOO_NEW`), les entrées inconnues sont ignorées (N9). (d) Chaque photo importée est **décodée puis ré-encodée** par l'`ImageCodec` de la plateforme et sa miniature régénérée : aucun octet d'origine inconnue n'est copié tel quel ; une photo indécodable est comptée et ignorée. (e) Les événements importés sont insérés par lots sans projection (`appendWithoutProjection`) puis la projection est **reconstruite une fois** ; la fusion est l'union des journaux par `id` (ADR-015). (f) L'export (photos pleine taille seulement, les miniatures sont régénérées à l'import ; pas de ZIP64 : au-delà de 65 535 entrées ou 4 Gio l'export échoue proprement — suivi noté) est écrit dans `exports/` du répertoire privé puis partagé par la feuille système (Android : copie dans `cache/share/` servie par un `FileProvider` non exporté, supprimée au prochain partage, au prochain lancement ou à l'effacement ; iOS : `ShareLink`) ; `SharedFactory.housekeeping()`, appelée par les hôtes après `warmUp()` à chaque lancement, purge les exports de plus de 24 h, les fichiers de la corbeille expirée et les restes d'`imports/`. (g) L'import prend un document choisi par l'utilisateur, **copié** par l'hôte dans `imports/` (le noyau ne lit jamais une URI étrangère), puis supprimé quel que soit le résultat. (h) **Annuler** (A13) = ajouter les événements inverses de la dernière écriture de cet appareil (groupe des événements partageant le même instant, par ex. `ItemCreated` + `ItemStored`) ; les événements importés et les opérations sans inverse exact (fusion/suppression de lieu, suppression de contenant, rappel accompli) sont refusés `NOT_UNDOABLE`. (i) **Corbeille** = 30 jours après `ItemDeleted` ou `PhotoDetached`, seuls les **fichiers** photo sont purgés ; journal et lignes restent, une restauration tardive rend la fiche sans ses images. (j) **Suppression totale** (H6, partie données) = `SharedFactory.wipeAllData()` ferme la base, supprime `db/`, `photos/`, `exports/`, `imports/` et rend l'instance inutilisable (`warmUp()` → `false`) ; l'hôte recrée une `SharedFactory` ; clés, préférences et notifications seront ajoutées à la procédure aux lots 8 et 9.
**Raison** : zéro dépendance et un seul format sur les deux plateformes ; une archive est une entrée hostile (zip bomb, chemins, images piégées) et doit être traitée comme telle ; le journal reste la seule source de vérité (annuler et corbeille n'effacent rien).
**Conséquences** : `docs/format-export.md` §5 décrit la sémantique d'import ; le `FileProvider` ne sert que `cache/share/` (jamais la base) ; toute nouvelle entrée d'archive doit être ajoutée aux limites et aux tests `ExportImportTest`.

## ADR-017 — 2026-10-26 — Vérification des sommes des dépendances Gradle
**Décision** : `gradle/verification-metadata.xml` (SHA-256 de chaque artefact et de ses métadonnées, plugins de build compris, signatures PGP non vérifiées) est versionné et la vérification est **stricte partout** (comportement par défaut de Gradle dès que le fichier existe), y compris sur le job macOS. Le fichier est produit par le workflow `Dependency verification metadata` (`--write-verification-metadata sha256 … --dry-run`, qui résout toutes les configurations des tâches de la CI sans les exécuter) enchaîné sur Linux puis macOS pour couvrir les artefacts Kotlin/Native et Apple, puis fusionné localement sous Windows pour les artefacts propres à ce poste (aapt2, distribution Kotlin/Native Windows). Le workflow se relance de lui-même quand le graphe de dépendances change (`libs.versions.toml`, `build.gradle.kts`, wrapper) ; la procédure est alors : télécharger l'artefact, l'installer dans `gradle/`, relancer l'écriture localement, commiter.
**Raison** : la défense contre une dépendance altérée en route reposait sur l'épinglage des versions et des dépôts filtrés ; la somme vérifiée ferme le cas du dépôt ou du miroir compromis. Une génération sur une seule plateforme aurait laissé le job iOS en échec ou en mode `lenient` (ce que la question ouverte du lot 1 proposait) ; la génération croisée rend le mode strict possible.
**Conséquences** : tout ajout ou montée de version de dépendance régénère le fichier (sinon la CI échoue avec la liste des artefacts manquants — jamais ajouter une somme à la main sans l'avoir obtenue par Gradle) ; les `trusted-artifacts` restent vides ; la vérification des signatures PGP est une évolution possible.

## ADR-018 — 2026-10-26 — Capture texte : règles du parseur et pipeline (lot 3)
**Décision** : (a) **Découpe objet / lieu** : après l'intent, la **première** préposition de lieu qui laisse un objet non vide ouvre le lieu, qui garde tout le reste de la phrase (« décos de Noël dans le carton 7 de l'étagère du fond de la cave » → lieu = « carton 7 de l'étagère du fond de la cave ») ; quand la phrase a une copule (« la boîte aux lettres **est** au crochet »), la coupe se fait après elle. Une préposition de **position** (`sous, derrière, devant, à côté de, au fond de, en haut de, en bas de, au-dessus de, contre, chez, près de` ; `under, behind, in front of, next to, on top of, at the back of, above, by, against`) **reste** dans le texte du lieu (« sous le canapé ») ; une préposition de simple localisation (`dans, sur, à, au, aux, @` ; `in, on, at, into, inside`) est **retirée**, ainsi que les déterminants de tête. Un « à » nu ne compte que devant un article (« à la cave »), jamais dans un nom (« clé à molette »). Cela tranche la question ouverte du lot 1 (option a + b) ; le corpus seed était déjà conforme. (b) **Lexique par langue, pas de LLM** (ADR-004) : fichiers de listes FR/EN (prépositions, articles, hésitations, nombres en lettres, unités, verbes de chaque intent), comparaison sur des clés **repliées** (minuscules sans accents : « ou est » vaut « où est »), tokenisation commune aux phrases et au lexique (élisions `l'`, `j'`, ponctuation, `@`). Ordre des reconnaisseurs : question → prêt → emprunt → retour de prêt → prise → remise → déplacement → rangement (défaut) ; un groupe nominal nu est un rangement sans lieu à faible confiance. (c) **Résolution de lieu** : score = max(Levenshtein normalisée sur nom, alias et chemin ; Jaccard des mots ; scoreur externe optionnel pour les embeddings du lot 6) ; ≥ 0,85 résolu, 0,6–0,85 proposition (B7, l'alias est mémorisé par un `PlaceRenamed`), sinon création ; les textes à plusieurs niveaux sont parcourus de droite à gauche (le plus long suffixe connu devient le parent) et le reste est proposé **en un seul niveau** sous le parent connu (l'utilisateur affine). (d) **Contenants** : un niveau créé dont le nom commence par un mot de contenant (« carton 7 », « boîte rouge », « box 3 ») devient un `Container` (numéro extrait) sous le lieu parent, pas un `Place`. (e) **Doublons (A14)** : noms d'objets actifs à ≥ 0,85 de similarité → la carte propose « déplacer l'existant » ou « créer » ; les verbes de mouvement agissent sans demander sur une correspondance ≥ 0,85, sinon demandent. (f) **Pipeline** : `CaptureService.propose()` n'écrit rien ; `commit()` passe par les commandes du lot 1 avec `source = TEXT` et `rawInput` = la phrase ; une question devient une recherche (lot 6 ; en attendant, filtre sur le nom). (g) **Corpus** : `corpus/parser.jsonl` est **généré** par `corpus/build-parser-corpus.py` (phrases écrites par le développeur, `origin: synthetic`) ; `ParserCorpusTest` (JVM) et `tools/evalParser` rejouent le même code (`ParserCorpus`), FR et EN notés séparément, seuils 95 % / 90 % jamais abaissés.
**Raison** : des règles lisibles et un corpus rejoué donnent un comportement prévisible et corrigeable phrase par phrase ; la préposition de position porte un sens que l'utilisateur veut retrouver (« sous le canapé » n'est pas « canapé ») alors que « dans le tiroir » n'ajoute rien au lieu « tiroir ».
**Précisions après revue** : (h) une phrase est bornée à 500 caractères, 80 mots et 20 objets (`INPUT_TOO_LONG`, rien n'est comparé ni écrit au-delà) et chaque texte du journal à 1 024 caractères (`CommandContext.MAX_TEXT`, sous la ligne de 64 Kio de l'import) ; (i) la similarité est calculée mot à mot quand les deux textes ont le même nombre de mots — le mot le plus éloigné décide et un nombre doit être identique (« carton 8 » n'est pas « carton 7 », « passeport de Léo » n'est pas « passeport de Léa »), les pluriels et accents sont repliés ; deux lieux à égalité (« tiroir » dans deux pièces) donnent une proposition, jamais un choix silencieux ; (j) `commit()` n'est pas transactionnel (une commande = une transaction) mais tout refus connaissable est levé **avant** la première écriture, et la carte annule exactement les événements écrits (`UndoService.undo(events)`), même répartis sur plusieurs instants ; (k) la question « déplacer l'existant ou créer ? » est décidée par le noyau (`CaptureProposal.nextQuestion`, réponses positionnelles `ItemChoice`), les écrans ne font qu'afficher ; (l) un niveau créé sous un contenant est créé dans le lieu du contenant (un contenant ne contient pas de lieu) ; (m) les écrans n'observent que les noyaux dont la base s'est ouverte (`App.readyShared`, `AppContainer.ready`) : après un effacement total la liste repart du nouveau noyau, et un stockage indisponible affiche une explication au lieu d'ouvrir la base.
**Conséquences** : chaque bug de capture ajoute une phrase au générateur du corpus ; un nouveau verbe ou une nouvelle préposition se déclare dans `Lexicon.kt` ; les embeddings du lot 6 se branchent par le scoreur externe de `PlaceResolver` et `DuplicateDetector` sans changer les seuils.

## ADR-019 — 2026-10-27 — Lieux, contenants et fiche objet (lot 4)
**Décision** : (a) **Modèle de lecture de navigation** : `BrowseRepository` (noyau) dérive des tables projetées ce qu'un écran affiche — `PlaceContent` (lieu, chemin racine → lieu, sous-lieux, contenants, objets rangés **directement** dans le lieu, photos) et `ContainerContent` ; les objets épinglés (D7) viennent en premier ; les lieux fusionnés ou supprimés n'apparaissent jamais ; l'écran ne calcule rien. (b) **Modèles de lieux (D2)** : listes FR/EN dans le noyau (`PlaceTemplates`), proposées **seulement** quand il n'existe aucun lieu, jamais créées sans un geste ; un modèle = un lieu racine et ses pièces écrits en une seule validation (un événement par lieu). (c) **Contenants (A3)** : un contenant vit dans un lieu, jamais dans un autre contenant ni l'inverse ; ce qui est créé « sous » un contenant est créé dans le lieu du contenant (ADR-018 l) ; **déplacer un contenant = un seul événement** `ContainerMoved` (D4), les objets qu'il contient en dérivent leur chemin ; un contenant ne se supprime que vide. (d) **Fusion (D6)** : `PlaceMerged` marque `mergedInto` sur le lieu absorbé ; ses objets, contenants et sous-lieux suivent ; aucun événement n'est réécrit ; les écrans excluent le lieu et ses descendants de la liste des cibles. (e) **Photos (A10, D5, U2)** : choix dans la photothèque par le sélecteur système (`PickVisualMedia` / `PhotosPicker`, aucune permission) ou prise de vue par la caméra système (permission demandée au premier usage, `NSCameraUsageDescription` FR/EN ; Android écrit la prise dans le cache `camera/` exposé par le `FileProvider`, jamais dans la galerie) ; les octets passent toujours par le codec du noyau (ré-encodage, EXIF retiré) ; un format illisible affiche « format non pris en charge » et n'écrit rien. (f) **Historique (A5)** : l'affichage est un **réglage d'affichage par appareil** (préférences `ui` / `UserDefaults`), pas une donnée métier ; le journal n'est lu que pendant qu'il est affiché. (g) **Pont Swift** : un flux remis à Swift via `FlowWatcher<T>` ne doit **jamais émettre `null`** (le rappel reçoit un `T` non optionnel) : `observeContainer` et `observeItem` du noyau s'arrêtent au lieu d'émettre `null` quand l'entité disparaît, et l'écran se ferme sur l'ordre explicite de la commande (`gone`) ; `bytesOf(NSData)` copie une photo en `ByteArray` en une fois. (h) **Tests de plateforme Android** : `androidApp/src/androidTest` (pilote SQLite : fichier sous `no_backup`, WAL, `synchronous=FULL` ; codec : orientation EXIF 6, PNG transparent aplati sur blanc, réduction sans agrandissement, octets non image → `null` ; parcours U1 texte en test Compose) exécutés sur un **Gradle Managed Device API 29** (`api29`, Pixel 2, image `aosp`) par un troisième job de CI avec KVM ; `lint { checkDependencies = true }` couvre `shared/androidMain`.
**Raison** : la navigation par lieu est de la lecture pure et doit donner le même résultat sur les deux plateformes ; les modèles de lieux répondent à « valeur dès le premier objet » sans imposer une configuration ; la règle « un événement par déplacement de contenant » est ce qui rend l'historique honnête (U5) et l'import idempotent ; les sélecteurs système évitent toute permission photothèque (H9).
**Précisions après revue** : (i) les règles « numéro d'un contenant déduit du libellé », « une unité de moins, jamais sous zéro » (`ItemCommands.decrement`) et « rien sur le disque sans événement » (`PhotoAttacher` : taille bornée à 48 Mio, ré-encodage, attache, suppression des fichiers si l'attache est refusée) vivent dans le noyau, pas dans les écrans ; (j) `ItemUpdated.clearUnit` (champ additif) efface l'unité seule ; une quantité illisible n'est jamais interprétée comme un effacement (le bouton Enregistrer reste inactif) ; (k) les objets archivés (D11) restent listés, en fin de liste et étiquetés, et leurs tags ne nourrissent plus les suggestions ; (l) la prise de vue Android survit à la mort du processus (chemin dans `rememberSaveable`), le dossier `cache/camera/` est purgé au lancement, le bouton n'apparaît que si une application caméra répond ; les images choisies sont lues bornées (taille déclarée puis flux) ; (m) `PrivacyInfo.xcprivacy` déclare `UserDefaults` (raison CA92.1) dès ce lot ; H6 efface aussi les préférences d'affichage sur les deux plateformes ; la fiche objet suit les changements écrits par le noyau (champs re-initialisés quand l'objet stocké change).
**Conséquences** : le job de CI « Android platform tests » vérifie les dépendances en mode `lenient` (les artefacts du lanceur de tests UTP ne sont résolus que pendant l'exécution, hors du dry-run du workflow de métadonnées — ADR-017) ; les deux autres jobs restent stricts. HEIC n'est pas couvert par les tests d'appareil (l'émulateur ne sait pas encoder) : à vérifier sur un appareil réel. Le pack d'une photo en pleine résolution via le pont Swift fait une copie mémoire (quelques Mio) : acceptable, à revoir si l'embedding d'image du lot 7 traite des rafales.

## ADR-020 — 2026-10-30 — Capture vocale et points d'entrée (lot 5)
**Décision** : (a) **Voix seulement si la reconnaissance sur l'appareil est garantie** : `SpeechPolicy` (noyau) décide `ON_DEVICE` / `NOT_ON_DEVICE` / `NO_RECOGNIZER` à partir des faits de la plateforme. Android : `SpeechRecognizer.isOnDeviceRecognitionAvailable` puis `createOnDeviceSpeechRecognizer` (API 31+), jamais `createSpeechRecognizer`. iOS : `supportsOnDeviceRecognition` et `requiresOnDeviceRecognition = true`, jamais relâché. **Android 10–11 passent en saisie texte** avec une explication : `EXTRA_PREFER_OFFLINE` n'est qu'un indice et le service de reconnaissance (appli Google, qui a Internet) peut envoyer l'audio à un serveur sans que l'app le sache — contraire à B2 et à « aucune donnée ne quitte l'appareil ». Le cahier des charges l'admet (N1 « < 5 s avec repli texte ailleurs ») ; le pack Whisper reste l'option si la mesure montre que c'est nécessaire. (b) **Permission au premier usage (H9)** : un tap sur le micro explique d'abord (« le son ne quitte jamais l'appareil et n'est pas conservé »), puis demande `RECORD_AUDIO` (Android) ou la reconnaissance vocale puis le micro (iOS) ; un refus laisse la saisie texte et propose les réglages du téléphone. (c) **La transcription est une phrase comme une autre** : elle passe par le même `CaptureService`, avec `source = VOICE` (la phrase tapée reste `TEXT`) ; « Défaire » émet les événements inverses avec la source de la capture ; l'audio n'est jamais écrit. Fin de phrase : résultat final du système (Android), ou 1,5 s de silence après les derniers mots, 5 s sans aucun mot (iOS). (d) **Points d'entrée (B5)** : Android — `CaptureActivity` translucide (tâche à part, hors des récents, non exportée, lancée par des `PendingIntent` immuables de l'app), widget **RemoteViews** sans bibliothèque (deux boutons, voix et texte, aucune mise à jour périodique — Glance aurait ajouté une dépendance et ses sommes de vérification pour deux boutons), tuile de réglages rapides qui ouvre la voix (`unlockAndRun` sur téléphone verrouillé). Android n'offre pas de widget d'écran verrouillé sur téléphone : la tuile en tient lieu. iOS — `CaptureIntent` (App Intent, `openAppWhenRun`, la reconnaissance exige le premier plan) exposé par `AppShortcutsProvider` à Siri, Raccourcis et au bouton Action ; extension WidgetKit (`systemSmall`, `systemMedium`, `accessoryCircular`, `accessoryRectangular`) qui ouvre `trouvetout-proto://capture?mode=voice|text` et ne lie pas le noyau. Aucune URL ni aucun extra ne transporte d'identifiant : une URL inconnue est ignorée ; comme toute app peut ouvrir le schéma d'URL iOS, une écoute lancée par une URL **n'enregistre rien d'elle-même** : la phrase entendue attend dans le champ le tap sur « Envoyer » (l'App Intent et le bouton micro, déclenchés par l'utilisateur, enregistrent directement) ; sur Android, une question posée dans la capture rapide passe à l'accueil par la mémoire du processus (`App.searchRequest`), jamais par un extra d'Intent que l'activité exportée recevrait d'une autre app. (e) **Mode « je range » (B10)** : `CaptureService.proposeIn(texte, lieu)` range dans le lieu ou le contenant choisi toute phrase de rangement qui ne nomme pas de lieu ; une phrase qui en nomme un, un mouvement ou une question suivent leur cours normal ; si le lieu a disparu, la question habituelle revient. (f) **Question vs affirmation (C5)** : déjà tranché par le parseur (intent `QUERY`) ; depuis la capture rapide Android, une question ouvre l'accueil sur la recherche.
**Raison** : la garantie « sur l'appareil » est la seule vérifiable par l'app ; un indice ne suffit pas pour une promesse de confidentialité. Les points d'entrée restent minimes (aucune donnée affichée) pour que H4 soit vrai par construction.
**Conséquences** : sur Android 12+ sans pack de langue hors ligne, le message invite à l'installer dans les réglages du téléphone (`triggerModelDownload`, API 33, possible plus tard) ; la dictée réelle n'est vérifiable que sur un appareil (les émulateurs n'ont pas le pack) ; N1 reste **à mesurer sur appareil**. Le micro du clavier (Gboard, clavier iOS) reste disponible dans le champ texte : c'est la dictée du clavier, hors du contrôle de l'app, à traiter avec la question ouverte sur l'apprentissage du clavier (lot 8). La garantie « sur l'appareil » est vérifiée statiquement par `tools/check-network.sh` (aucun `createSpeechRecognizer(`, `requiresOnDeviceRecognition = true` exigé, widgets sans accès au noyau) : un compteur réseau de l'app ne verrait pas un service de reconnaissance qui tourne dans un autre processus. La permission `RECORD_AUDIO` et `NSMicrophoneUsageDescription` / `NSSpeechRecognitionUsageDescription` entrent dans les fiches magasin (aucune donnée collectée : l'audio ne quitte pas l'appareil).

## ADR-021 — 2026-10-31 — Recherche hybride et modèle embarqué (lot 6)
**Décision** : (a) **Mots-clés : index inversé en mémoire dans `shared`**, pas de FTS5 : le SQLite système d'Android n'a pas FTS5 (les tests JVM et iOS seraient passés, l'app aurait échoué en API 29) et FTS ne tolère pas les fautes. `KeywordIndex` : BM25 sur champs pondérés (nom 3, étiquettes 2, lieu et contenant 1,5, description 1, deux dernières phrases dictées 0,5), mêmes règles de texte des deux côtés (`SearchText` : accents et casse repliés, mots composés aussi joints, pluriels, mots grammaticaux retirés), complétion du dernier mot, fautes par distance d'édition (1 dès 4 lettres, 2 dès 8) contre le vocabulaire des fiches et des synonymes, et par clé phonétique française (« sizeaux » → ciseaux), synonymes FR/EN d'un seul saut (`Synonyms.kt`, poids 0,7). Reconstruit quand le journal change (nombre d'événements + tête). (b) **Modèle : EmbeddingGemma 2 Text 270M (int4, 165 Mo, Apache 2.0) inclus dans l'app** — révise ADR-008 pour ce fichier ; `models/manifest.json` épingle la révision Hugging Face et le SHA-256, `:models:fetchTextModel` télécharge et vérifie au build, rien n'est versionné ; pas de `ModelPackDownloader`, aucune permission réseau. Android : asset non compressé, copié une fois dans `cacheDir/models/` (LiteRT-LM ouvre un fichier ou un descripteur sans décalage, pas une entrée d'APK) ; iOS : ressource du bundle lue en place ; `-Ptrouvetout.bundleModel=false` produit une app sans modèle. (c) **Runtime : LiteRT-LM** 0.19.0 sur Android et la JVM (`litertlm-android`, `litertlm-jvm` pour l'évaluation), 0.18.1 pour le Swift Package `LiteRTLM` (le tag 0.19.0 associe des sources Swift plus récentes que le binaire 0.18.1 qu'il désigne ; même binaire des deux côtés de toute façon) — même fichier, même tokenizer intégré ; CPU seulement ; ABI arm64-v8a et x86_64 uniquement : un téléphone 32 bits reste en mots-clés. Swift implémente le modèle via `CallbackTextModelSource` (Swift ne peut pas implémenter une fonction `suspend`). (d) **Vecteurs** : préfixes de tâche de la fiche du modèle (`task: search result | query:` / `title: none | text:`), 256 dimensions (Matryoshka), texte = nom + description + étiquettes + « Rangé : racine, pièce » (le contexte d'une fiche nue comme « Louche » ; les niveaux plus fins restent au mot-clé, un déplacement dans la pièce ne recalcule rien), coupé à 400 caractères (LiteRT-LM refuse une entrée trop longue au lieu de la tronquer), stockés en float16 dans la table cache `embedding` (`model_key` = modèle + dimension + préfixes, `text_hash`), jamais exportés, recalculés au premier plan seulement (N6) et effacés pour un ancien modèle une fois les nouveaux complets. Chargement paresseux, une utilisation à la fois, libéré quand l'app passe en arrière-plan ou sur avertissement mémoire. (e) **Fusion linéaire** : 0,3 × score mot-clé relatif au meilleur (0,6 quand la meilleure fiche contient tous les mots de la question) + le reste × force sémantique, la force étant l'écart du cosinus à la moyenne des 50 candidats sur 0,1 (borné à [0, 1]) : une question que le modèle ne reconnaît pas (mot inconnu, faute) ne fait ressortir aucun candidat et pèse peu ; puis ×(1 + 0,1·exp(−jours/90)) pour la récence et jusqu'à +10 % pour la fréquence d'ouverture (`search_usage`). (f) **Réponse C4 en données** (`AnswerLine` : chemin cliquable, contenant, état, date, photo), mise en phrase par chaque UI avec ses formatteurs de date ; suggestions C12 par complétion des noms, étiquettes et lieux, jamais d'un objet sensible, sans historique de requêtes ; filtres C11 (lieu et sous-lieux, contenant, étiquette, état, déplacé depuis). (g) **Évaluation** : corpus de 406 fiches et 360 questions (+ 20 « absentes »), écrit puis audité par des passes indépendantes qui n'ont lu ni le moteur ni ses résultats, split `dev`/`holdout` (un sur cinq) ; tous les réglages sur `dev` seulement ; `tools/eval-search` en CI (job `search-eval`, Java 21) avec le vrai modèle.
**Raison** : mesures du lot sur le corpus (hybride, FR / EN, top-1 / top-3) : mots-clés seuls 63,3 % / 73,7 % et 78,3 % / 83,3 % ; sémantique seule 77,0 % / 90,3 % et 96,7 % / 98,3 % ; **hybride 82,3 % / 92,3 % et 96,7 % / 100 %** (holdout FR 75,0 % / 81,7 %) ; latence p95 132 ms sur 5 000 objets (N2 tenu). Les trois derniers gains (part du mot-clé quand il couvre toute la question, racine et pièce dans le texte vectorisé, clé phonétique) viennent de l'évaluateur de qualité et remontent aussi le holdout (70,0 → 75,0 %), signe qu'ils généralisent ; un lexique de marques et de mots familiers a été écarté faute de source indépendante du corpus ; mémoire de l'app sur l'émulateur API 29 avec le modèle chargé : 212 Mo sales (PSS 434 Mo, dont 213 Mo de pages propres du fichier projeté et de l'APK, récupérables par le système). Variantes mesurées et écartées : RRF (sans écart de score, le bonus de récence inversait les rangs : 61 % top-1 FR), préfixes du guide LiteRT-LM ou aucun préfixe (−1 à −9 points), 768 dimensions (pas mieux en FR, trois fois plus gros), nom en `title:` ou phrase dictée ajoutée au texte vectorisé (dans le bruit, EN en baisse), pénalité de « hubness » vers le centroïde (pas de gain).
**Conséquences** : **N3 est atteint en top-1 mais pas en top-3 en français** (92,3 % pour 95 %) : la CI bloque sous un plancher qui ne baisse jamais (`SearchCorpus.FLOORS` : FR 81,5 % / 91,5 %, EN 95 % / 98 %, mesure moins une question) et affiche l'objectif ; pistes : variante 440M/740M sur les téléphones ≥ 6 Go (lot 7), reclassement par le petit LLM (lot 11), lexique domestique enrichi. La limite de 200 Mo du module de base sur Play impose de livrer le fichier en pack d'assets *fast-follow* au lot 12 (chemin de fichier direct, plus de copie) ; d'ici là l'app installée occupe environ 2 × 165 Mo (APK + copie) plus 71 Mo de cache XNNPACK. Le lot 7 devra trancher entre inclure la variante omnimodale (485 Mo) et un pack. Licences : mention Apache 2.0 d'EmbeddingGemma 2 et de LiteRT-LM dans les réglages ; `THIRD_PARTY_NOTICE` de LiteRT-LM à reprendre dans la page J7. La réponse en une ligne s'affiche aussi quand la question vise un objet absent proche (« le fer à friser » → fer à repasser) : le seuil « rien trouvé » ne joue que sans aucun mot commun.

(g) **Recherche par photo (C10)** : la photo de la question (jamais stockée) contre les photos des objets (image ↔ image) et les textes des fiches (image ↔ texte), fusion linéaire sur **seuils absolus** (`Ranking.combinePhoto` : force = (cosinus − plancher) / 0,05 bornée à [0, 1] ; plancher 0,80 et part 0,6 pour image ↔ image, plancher 0,70 et part 0,4 pour image ↔ texte) ; rien au-dessus des planchers = « aucun objet ne ressemble à cette photo ». ## ADR-023 — 2026-11-01 — Vie privée et sécurité : base chiffrée, verrouillage, objets sensibles (lot 8)
**Décision** : (a) **Chiffrement au repos (H2) de la base seule, par SQLCipher 4.19** (`net.zetetic:sqlcipher-android` 4.19.1 ; paquet Swift `SQLCipher.swift` 4.19.0 épinglé par commit, xcframework vérifié par la somme de son manifeste ; licence de type BSD, attribution dans les réglages). Clé : 32 octets aléatoires passés en **clé brute** (`x'…'`, sans dérivation PBKDF2 : ouverture rapide, la clé n'est pas un mot de passe) ; Android : enveloppée par une clé AES-256-GCM du Keystore (StrongBox quand le téléphone en a, sans authentification de l'utilisateur pour que le widget et la tuile écrivent), fichier `no_backup/keys/db.key` ; iOS : élément Keychain `AfterFirstUnlockThisDeviceOnly`, non synchronisé, géré par le noyau (`IosDatabaseKeys`) au travers d'un accès Swift minimal (`KeychainDatabaseKey`). **Les photos ne sont pas chiffrées par l'app** (décision de l'utilisateur du 1er nov.) : conteneur privé, chiffrement du système (FBE ; `NSFileProtectionCompleteUntilFirstUserAuthentication`), exclues des sauvegardes. (b) **Migration des bases en clair des lots 1 à 7** (`DatabaseEncryption`, noyau) : une base dont l'en-tête est `SQLite format 3` est copiée par `sqlcipher_export` dans `<base>.enc` après un `wal_checkpoint(TRUNCATE)` complet (sinon rien n'est fait), la clé passée en paramètre lié (`ATTACH … KEY ?`, jamais dans un texte SQL qu'une erreur journaliserait), la copie est rouverte avec la clé et comparée (version du schéma, nombre de lignes de chaque table), les fichiers annexes de l'ancienne sont supprimés, puis la copie est renommée par-dessus (`rename(2)`, atomique). Tout échec avant le renommage laisse la base en clair intacte et le lancement suivant recommence (la copie orpheline est supprimée d'abord). Un fichier chiffré sans clé n'est jamais remplacé : `DatabaseKeyLostException`, puis un écran « vos objets ne peuvent pas être lus » qui propose l'effacement total et l'import d'un export. Chaque ouverture exige une réponse à `PRAGMA cipher_version` : un SQLite du système lié par erreur (iOS : `-lsqlite3` retiré, `linkSqlite` de SQLDelight désactivé ; Android : pilote `SupportOpenHelperFactory`) est refusé plutôt que d'écrire en clair. L'effacement total (H6) supprime la clé. (c) **Verrouillage (H3)**, optionnel, désactivé par défaut : `BiometricPrompt` du framework Android (API 29 : `setDeviceCredentialAllowed` ; API 30+ : `BIOMETRIC_STRONG | DEVICE_CREDENTIAL`, pas la reconnaissance faciale 2D de classe 2 ; pas d'androidx.biometric) et `LAContext.deviceOwnerAuthentication` (Face ID, Touch ID ou code) ; aucun mot de passe propre à l'app (rien à oublier, rien à récupérer sans serveur). L'état est dans le noyau (`AppLock`, `PrivacySettings`, `meta`) : verrouillé au lancement, puis après un délai d'absence (immédiat, 1 min, 5 min) ; le temps d'absence est le plus long de l'horloge murale et d'une horloge monotone, et une horloge murale reculée verrouille (la monotone s'arrête en veille profonde ; la murale peut être reculée par qui tient le téléphone déverrouillé) ; un aller-retour annoncé vers un écran du système (appareil photo d'Android, feuille de partage, sélecteur de fichier, réglages) laisse une grâce d'une minute. Activer ou désactiver le verrou demande l'authentification ; un téléphone sans code ne peut pas l'activer, et un téléphone dont le code a été retiré s'ouvre. Tant que l'état n'est pas « déverrouillé », le contenu est couvert et caché aux lecteurs d'écran (fermé par défaut) ; verrou actif : `FLAG_SECURE` sur les deux activités Android, vue de protection iOS dès que la scène n'est plus active. La capture rapide d'Android reste possible app verrouillée : elle n'affiche que sa propre carte ; le noyau n'y propose aucun objet sensible ni aucune liste de lieux tant que l'app est verrouillée (`CaptureService.locked` ; l'app déverrouillée agit toujours sur eux, sans doublon) et la capture rapide compte comme un retour dans l'app pour le délai et toute question (lieu à confirmer, objet existant) renvoie la phrase à l'accueil verrouillé ; l'invite du code d'Android 10, une activité à part, ne compte pas comme un départ (`AppLock.authenticationStarted`) ; `CaptureIntent` iOS exige un iPhone déverrouillé (`authenticationPolicy`) et une capture demandée sous le verrou attend le déverrouillage ; iOS ferme feuilles et alertes quand l'app part verrou actif (elles s'afficheraient au-dessus de la couverture). (d) **Objets sensibles (H4)** : interrupteur « objet sensible » dans la fiche (`ItemUpdated.sensitive`, champ existant depuis le lot 1) ; jamais dans la liste d'accueil (`ItemRepository.observeListed`), les suggestions (C12, A11) ni les miniatures (`AnswerLine.photoThumbName` nul, `AnswerLine.sensitive`) ; dans un lieu ou un contenant, une ligne « N objets sensibles masqués » (`PlaceContent.hidden`, `ContainerContent.hidden`) les affiche sur demande ; la recherche les trouve toujours ; verrou actif, ils ne s'affichent (lignes, réponse, résultats) qu'après l'authentification, jusqu'au passage en arrière-plan (`AppLock.revealed`). Un contenant qui n'a que des objets sensibles n'est pas vide. Widgets, tuile et notifications n'affichent aucun objet (vrai par construction depuis le lot 5). (e) **Clavier** (question ouverte du lot 3) : réglage séparé, désactivé par défaut, « empêcher le clavier d'apprendre ce que je tape » : Android ajoute `IME_FLAG_NO_PERSONALIZED_LEARNING` à tous les champs de l'app (`InterceptPlatformTextInput`, une demande que le clavier peut ignorer) ; iOS n'a pas d'équivalent public, la section le dit. (f) **Permissions (H9)** : explication avant l'invite caméra d'iOS et renvoi vers les Réglages après un refus, pour tous les boutons photo (`AddPhotoButtons`) ; `USE_BIOMETRIC` (permission normale, sans invite) ; `NSFaceIDUsageDescription` FR/EN. Android prend les photos par l'application Appareil photo, sans permission (ADR-019). (g) **Mode simplifié (I7)** : préférence d'affichage de l'appareil, comme l'historique (ADR-019 f) : l'accueil n'a plus que « Ranger » (la voix, ou le clavier quand la reconnaissance sur l'appareil manque) et « Retrouver », les réglages restent en haut ; thème système (I8) déjà suivi par les deux apps. (h) **Vérifications automatiques** : `tools/check-deps.sh` refuse le travail en arrière-plan (N6 : WorkManager, JobScheduler, service au premier plan, BGTask, `UIBackgroundModes`), une permission non prévue dans le manifeste fusionné de la release et une ABI hors `arm64-v8a`, `armeabi-v7a`, `x86_64` ; `tools/check-logs.sh` refuse tout appel de journalisation hors du `Logger` injecté ; `tools/check-native-network.sh` (CI macOS) refuse un symbole réseau dans LiteRT-LM et SQLCipher ; accessibilité (I6) : Accessibility Test Framework dans les tests Compose (API 29) et `performAccessibilityAudit` dans une cible XCUITest. (i) **ABI** : `armeabi-v7a` est gardée (SQLCipher seul, sans LiteRT-LM) : un téléphone 32 bits s'installe et cherche par mots-clés (ADR-021) ; `x86` 32 bits est retirée (`abiFilters`).
**Raison** : le SQLite chiffré protège l'inventaire si le stockage est extrait (téléphone volé, sauvegarde copiée par un autre moyen) sans rien demander à l'utilisateur ; la clé brute évite 256 000 itérations de PBKDF2 à chaque ouverture ; la vérification `cipher_version` ferme le piège connu du SQLite du système lié à la place (base écrite en clair sans erreur). Les photos chiffrées auraient demandé des chargeurs d'image propres aux deux plateformes et un déchiffrement à chaque affichage, export et passage au modèle, pour une protection proche de celle du système. Le verrou s'appuie sur l'authentification du téléphone : une biométrie ou un code que l'utilisateur connaît déjà, et aucune récupération à prévoir. « Sensible » reste discret sans verrou (pas d'invite à chaque recherche) et devient une vraie barrière avec lui.
**Conséquences** : la première ouverture du lot 8 chiffre la base une fois (10 000 objets et 10 000 événements : moins de 1,8 s sur l'émulateur API 29) ; la connexion de migration Android est ouverte avec `CREATE_IF_NECESSARY` (une base attachée hérite des drapeaux d'ouverture) et l'`ATTACH` passe par `execSQL` (une seule connexion ensuite) ; l'APK gagne environ 5 Mo (`libsqlcipher.so`, trois ABI). **Export et chiffrement (Apple)** : SQLCipher apporte un algorithme standard (AES-256) hors du système d'exploitation : à la soumission (lot 12), `ITSAppUsesNonExemptEncryption = YES` et, pour une distribution en France, la déclaration de chiffrement française à téléverser dans App Store Connect (Apple, « Export compliance documentation for encryption ») ; la clé n'est pas encore posée dans `Info.plist` tant que rien n'est soumis. Google Play ne demande pas de déclaration équivalente. La politique de confidentialité (J7) dit exactement : la base (objets, lieux, historique) est chiffrée sur le téléphone, les photos sont protégées par le chiffrement du téléphone, le verrouillage utilise l'empreinte, le visage ou le code du téléphone que l'app ne voit jamais ; avec l'attribution de SQLCipher. **Risques résiduels acceptés** : un export (ZIP en clair, photos comprises) reste jusqu'à un jour dans `exports/` et sa copie de partage dans le cache, le temps que la feuille de partage le lise ; le littéral de la clé est une chaîne qui reste en mémoire le temps du processus ; l'élément Keychain survit à la désinstallation d'iOS (sans base, il ne protège plus rien) ; les réglages du verrou et du clavier sont dans `meta`, ni exportés ni restaurés par un import. La clé Android est écrite et synchronisée sur le disque (`fsync` du fichier et du dossier) avant le chiffrement, l'élément Keychain n'est jamais remplacé, et une erreur du Keychain autre que « absent » rend le stockage indisponible, jamais « clé perdue ».
