Format des données

Vos données doivent pouvoir se lire sans l'application, aujourd'hui comme dans dix ans. Voici comment est fait un export.

Format version 1. Un export v1 s'importe dans toutes les versions suivantes : le format n'évolue qu'en ajoutant des champs ou des types d'événements, jamais en renommant ni en supprimant. Un lecteur ignore ce qu'il ne connaît pas. Document de référence complet, avec le schéma SQLite : docs/format-export.md.

L'export ZIP

Réglages → Exporter crée trouvetout-export-AAAAMMJJ-HHMMSS.zip (heure UTC), que vous partagez où vous voulez. Il n'est pas chiffré.

manifest.json     { "formatVersion": 1, "appVersion": "…", "schemaVersion": 1, "exportedAt": <ms UTC>,
                    "deviceId": "…", "counts": { "events": n, "items": n, "places": n, "containers": n, "photos": n } }
events.jsonl      le journal complet, un événement JSON par ligne, trié par (at, deviceId, id)
snapshot.json     l'état courant, lisible d'un coup d'œil : items, places, containers, locations, photos, reminders
photos/<id>.jpg   les photos, recompressées (côté long ≤ 2048 px), sans leurs métadonnées d'origine

Pour un coup d'œil, ouvrez snapshot.json. Pour tout l'historique, events.jsonl (JSON Lines : un objet par ligne). snapshot.json n'est jamais réimporté : il est recalculé à partir du journal.

Le journal d'événements

Chaque action est un événement immuable, daté et signé par l'appareil ; rien n'est jamais écrasé. L'état courant (où est chaque objet) se déduit en rejouant le journal dans l'ordre.

Ce que contient un export

Tout, objets sensibles compris, et uniquement ce que vous avez saisi ou ce qui en découle : noms, descriptions, étiquettes, lieux et leurs alias, contenants, la phrase complète dite ou tapée, les noms des personnes à qui vous avez prêté un objet, les dates de vos actions, vos photos ré-encodées et l'identifiant aléatoire de l'installation (qui date votre premier lancement). Rien ne vient d'un capteur, d'un compte, d'un contact ou d'un identifiant du système. Les réglages du téléphone (verrouillage, préférences, date d'essai, état d'achat) n'y sont pas.

Importer

Réglages → Importer relit manifest.json, events.jsonl et photos/ ; les événements déjà connus sont ignorés, si bien qu'importer dans un téléphone qui a déjà des données fusionne les deux. Les photos sont ré-encodées, jamais copiées telles quelles. Limites : archive ≤ 1 Gio, journal ≤ 64 Mio, photo ≤ 48 Mio.

La sauvegarde chiffrée (.ttbk)

Un fichier .ttbk contient une archive d'export, chiffrée. Il s'ouvre avec la clé de secours, depuis l'application ou avec ces indications :

  • En-tête de 41 octets : TTBK, version (1 octet, 1), taille de bloc (4 octets, gros-boutiste, 1048576), sel aléatoire (32 octets).
  • Clé de secours : 28 caractères en base 32 de Crockford (tirets ignorés ; O se lit 0, I et L se lisent 1) : 16 octets de clé, 1 octet de contrôle (premier octet du SHA-256 de la clé), 4 bits nuls.
  • Clé du fichier : HKDF-SHA-256 (RFC 5869) de la clé de secours, avec le sel de l'en-tête et l'info trouvetout-backup-v1, 32 octets.
  • Blocs : l'archive coupée en blocs de 1 Mio, chacun scellé en AES-256-GCM (texte chiffré puis étiquette de 16 octets). Nonce de 12 octets : 3 octets nuls, numéro du bloc depuis 0 (8 octets, gros-boutiste), puis 1 pour le dernier bloc et 0 sinon. Données additionnelles : l'en-tête entier.

Altérer, réordonner, tronquer ou prolonger le fichier empêche de l'ouvrir.
